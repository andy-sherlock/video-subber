## 一、项目背景

### 1.1 这个项目是什么

视频中文字幕生成工具（video-subtitle）。用户拖一个视频进去，自动生成中文字幕。当前版本 V3.05，活跃代码在 `v2/` 目录下。

### 1.2 转录流水线

```
视频 → 提取音频 → 转录 → 幻觉过滤 → 翻译 → 字幕输出
```

转录阶段涉及三个模型（用户可选三档：快速/标准/精确）：

| 模型 | 角色 | 语言 |
|------|------|------|
| **Whisper large-v3** | 主力转录。产出带时间戳的句子段落 | 99 种语言 |
| **SenseVoice** | 声音分类。识别"人声/音乐/掌声/笑声/呼吸" | 不转录文字 |
| **Qwen3-ASR 1.7B** | 交叉验证转录。和 Whisper 听同一段音频，产出独立转录文字 | 52 种语言 |

精确档（tier=precise）三个模型全部启用。标准档只用 Whisper + SenseVoice。

### 1.3 千问的参数控制

千问通过 `_qwen_gen_kwargs()` 函数传参。关键参数：

```python
# v2/backend/core/qwen_asr_runner.py

_QWEN_REPETITION_PENALTY = 1.1   # 重复惩罚力度。1.0=不罚，1.4=重罚
_QWEN_REPETITION_WINDOW = 256    # 惩罚窗口（token数）
_QWEN_TOKENS_PER_SEC = 20        # 每秒token预算。300秒×20=6000 token上限
_QWEN_MIN_TOKENS = 256           # 最小token数兜底

def _qwen_gen_kwargs(duration_s, language=None, use_mlx=True):
    kwargs = {}
    if duration_s and duration_s > 0:
        cap = max(_QWEN_MIN_TOKENS, int(duration_s * _QWEN_TOKENS_PER_SEC))
        kwargs["max_tokens" if use_mlx else "max_new_tokens"] = cap  # cap就是max_tokens
    kwargs["repetition_penalty"] = _QWEN_REPETITION_PENALTY
    kwargs["repetition_context_size"] = _QWEN_REPETITION_WINDOW
    return kwargs
```

千问处理长音频时分段切块（chunk）。每个 chunk 最多 5 分钟（`_CHUNK_MAX_DURATION_S = 300`），在 Whisper 的自然段落边界处切割。每个 chunk 独立调用千问转录。

## 三、Bug 时间线

### 3.1 第一次：千问重复坍缩（P147）

**测试**：job 97c57255ec，24 分钟俄语视频，tier=precise

**现象**：
- 千问在音频前 2 分钟后陷入重复坍缩
- 从第 120 秒开始到结尾，每个 chunk 都输出同一串文字：`1056234897 НЕТ ТЫ МЕНЯ ПРОСТИ`
- chunk 5 单个 chunk 卡了 **13.5 分钟**（正常应该 ~2 分钟）
- 最终 198 段中 116 段（58%）的千问文字是这串垃圾
- 只有 9/198 段是真正的俄语内容

**根因**：旧代码调用千问时没有传任何生成控制参数，全吃默认值：
- `max_tokens` 不传 → 自动 = 时长 × 50 ≈ 15000/chunk。坍缩发生后没有熔断，狂吐到 15000 才停
- `repetition_penalty` = 1.2 默认，太弱，掰不开强重复环
- `repetition_context_size` = 100，重复周期超窗口后惩罚"失忆"
- `language` 不传 → 每个 chunk 独立重判语言（稳定性隐患）

**解决方案（初版，后被证实矫枉过正）**：

```python
# P147 初版修复（qwen_asr_runner.py 第 49-52 行，已废弃）
_QWEN_REPETITION_PENALTY = 1.4    # 1.2→1.4，加大惩罚
_QWEN_REPETITION_WINDOW = 256     # 100→256，扩大窗口
_QWEN_TOKENS_PER_SEC = 10         # 新增。50→10，收紧token预算
```

**问题**：三个参数同时向极端方向收紧。没有单独验证每个参数的效果。

### 3.2 第二次：千问 "不说话"（P156）

**测试**：job 0a73f157b2，同一段 24 分钟俄语视频，同 large-v3，同 tier=precise

**现象**：
- P147 目标达成：坍缩归零（58%→0%），chunk 5 从 13.5 分钟降到 2.2 分钟
- **新问题**：千问产出从 185 句暴跌到 **12 句**
- 交叉验证映射率从 85%（185/217）降到 **6%（12/186）**
- 日志证据：`Qwen->Whisper 使用 1:1 映射 (qwen=12 whisper=186)`

**根因定位**（排查过程）：

1. **排除对齐问题**：日志显示 `qwen=12` 是千问 raw 转录结果——不是对齐环节丢了，是千问本身就没说话
2. **排除俄语问题**：千问 3 对俄语的 FLEURS WER=5.99（约 94% 正确率），30 种语言排名第 13。不是"千问不擅长俄语"
3. **确认参数问题**：对比赛品 WhisperJAV 的同参数后发现 P147 在两个维度上同时处于极端值

| 参数 | P147 前（工作） | P147（坏了） | WhisperJAV（工作） |
|------|----------------|------------|-------------------|
| `repetition_penalty` | 1.2 | **1.4** | 1.1 |
| `max_tokens_per_second` | 50 | **10** | 20 |
| `repetition_context_size` | 100 | 256 | 不设 |

**主犯**：`repetition_penalty=1.4`。俄语是屈折语——名词变六个格，动词变位，形容词性数格一致。同一个词根在 256 token 窗口内反复出现十几次。惩罚力度 1.4 导致正常重复结构也被压制，千问提前终止生成。

**从犯**：`TOKENS_PER_SEC=10`。5 分钟 chunk = 3000 token 预算。正常俄语 5 分钟需要 2000-4000 token。3000 刚好在边界，无余量。

**协同效应**：1.4 让千问不敢说话 + 10t/s 让它没时间说话 = 93% 输出消失。

**终版修复（2026-06-05 二次校准，当前生效代码）**：

```python
# v2/backend/core/qwen_asr_runner.py 第 49-56 行（当前版本）
_QWEN_REPETITION_PENALTY = 1.1   # P156: 1.4→1.1; 对齐 WhisperJAV
_QWEN_REPETITION_WINDOW = 256    # 保持不动。范围合理，问题在惩罚力度
_QWEN_TOKENS_PER_SEC = 20        # P156: 10→20; 5min×20=6000 token（3×余量）
_QWEN_MIN_TOKENS = 256           # 保持不动
```

验证结果：

- 端到端测试 job 1b520de51c 跑完
- 千问产出 2062 句（P156 时 12 句），坍缩 0%
- 翻译 254/254 全成功（DeepSeek）
- 247 个单元测试全过

### 3.3 第三次：千问和 Whisper 对不上（P160）

**现象**：千问虽然恢复了正常输出（2062 句），但和 Whisper 的 254 段做交叉验证时，映射率只有 35%（92/266）。最终只产生了 **1 条**交叉验证信号。

**为什么 2062 句只剩 92 段？**

旧对齐算法 (`qwen_asr_runner.py` 中的 `_match_qwen_to_whisper` 和 `align_by_similarity`)：

1. 千问的每一句去和 Whisper 的 254 段逐字符比对（`SequenceMatcher`）
2. 相似度 < 0.2 的全部丢弃
3. 俄语词尾变形让同一个意思的字面相似度只有 50-70%
4. 2062 句 × 254 段 = 50 万次比对，最终只留下 92 段

```python
# 旧对齐逻辑（qwen_asr_runner.py 第 90-115 行）
def _match_qwen_to_whisper(qwen_sentences, whisper_segments):
    for qs in qwen_sentences:
        best_idx = -1
        best_score = 0.0
        for i, st in enumerate(segment_texts):
            score = SequenceMatcher(None, qs_key, st).ratio()  # 逐字符比较
            if score > best_score:
                best_score = score
                best_idx = i
        if best_score > 0.2:  # 俄语变形后经常低于0.2
            pairs.append((qs, best_idx))
    return pairs
```

**为什么逐字母比对对俄语无效**

俄语是屈折语。同一个词根据语法角色（主语/宾语/介词后/工具/...）改变词尾。中文里的"钱"永远写"钱"——俄语有六种写法：

| 语法角色 | 俄语写法 | 逐字母比对 |
|---------|---------|----------|
| 主语 | деньги | — |
| 否定后 | денег | 只 60% 字母相同 |
| 介词后 | деньгах | 只 55% 字母相同 |
| 间接宾语 | деньгам | 只 55% 字母相同 |

从三次测试的真实数据来看：

```
Whisper: Блин, по голове его постучало.
千问:   Поговори, поговори, мы постучала
→ 逐字母相似度 58%。同一个"敲/撞"（постучал-），词尾不同，开头不同

Whisper: Саш, привет. Я к тебе по делу.
千问:   Ладно, я к тебе по делу
→ 逐字母相似度 72%。核心"Я к тебе по делу"完全一样，但开头不同
```

## 四、终版架构方案（方向已定，实施方案待选）

### 4.1 核心原则

1. **每个工具只做一件事。** 重复检测管重复。语速检测管物理。SenseVoice 管"有没有人说话"。千问管"说出来的是什么"。
2. **没有人单独做决定。** SenseVoice 和千问在非人声区域要双重确认。一个人说"非人声"另一个人说"有人声"→不自动判。
3. **不翻译全量。** 只在"有争议的片段"上做翻译确认。大部分片段两个模型说法一致，不需要翻译。

### 4.2 新流水线架构

```
音频
  ↓
SenseVoice 扫全音频 → 画"声音地图"
（标注每个区间：Speech / BGM / Breath / Applause / Laughter / ...）
  ↓
Whisper + 千问分别转录
  ↓
═══════════════════════════════════
三层防线
═══════════════════════════════════
  ↓
第一层：SenseVoice + 千问 双重确认（针对非人声区域）
  
  SenseVoice 标"非人声" + 千问也没说话 → 一致 → Whisper写了字=幻觉，自动标红
  SenseVoice 标"非人声" + 千问说了话 → 矛盾 → 标记可疑，不自动删除
  SenseVoice 标"人声" → 进入第三层
  ↓
第二层：重复检测 + 语速异常（现有逻辑，不改）
  
  连续5句一模一样的 "Да." → 丢弃
  0.5秒说了570个字 → 物理不可能，丢弃
  ↓
第三层：千问 B+A 窗口比对（仅 SenseVoice 标记为"人声"的区域）
  
  Step A — 时间对齐：
    把音频按30秒一格切成窗口（24分钟≈48个窗口）
    每个窗口内，Whisper和千问在同一个时间段说了什么
    
  Step B — 词干提取（非逐字母比对）：
    每个词裁掉"尾巴"，只留"骨头"（词干）
    
    中文：不裁。汉字本身不变形
    英语：Porter Stemmer。running→run, walked→walk, dogs→dog
    俄语：Snowball Stemmer。денег→ден, деньгах→ден
    日语：滤除助词（は/が/を/に/の/で/へ/と/から/まで）。"私は学生です"→"私 学生"
    韩语：滤除助词（은/는/이/가/을/를/에/에서/로/와/과）
    
  Step C — 窗口内比对：
    每个窗口内，看Whisper和千问有多少个共享词干
    共享超过门槛 → 盖绿章"一致"
    共享不够 → 盖黄章"待确认"
    
  Step D — 汇总统计：
    48个窗口中40个绿章，3个黄章（5个跳过/非人声）
    → 一致率：40/43 = 93%
    
  Step E — 仅对黄章窗口做LLM翻译确认：
    3个黄章窗口 → 几百个词 → 几块钱的LLM费用
    不是翻译整部视频的1214个词
```

### 4.3 非人声区域的判定决策表

| SenseVoice 说 | 千问说 | 结论 | 动作 |
|-------------|------|------|------|
| 非人声（Breath/BGM/Applause等） | 没说话 | 一致 | Whisper写了字 → 判幻觉，自动标红 |
| 非人声 | 说了话 | 矛盾 | **不自动判。** 标记可疑，留给人工或LLM确认 |
| 人声（Speech） | 任意 | 走第三层 | B+A窗口比对 |

### 4.4 方案设计中的争议与修正过程

> **注意**：以下流水线方案是经过 Steve Jobs 多轮审查的结果，但用户（项目负责人）在审查过程中提出了若干关键质疑，部分问题已解决，部分仍待确认。本节如实记录整个讨论过程。

---

#### 争议一：SenseVoice 在新流水线中是否被调用了两次？

**用户的质疑**：流水线图中 SenseVoice 在"提取音频之后"出现了一次，又在"Whisper/千问转录之后"作为第一层防线出现了一次。用户问——为什么调用了两次？

**核实结果**：当前代码中 SenseVoice 只调用了一次（`transcriber_v2.py` L283-292）。产出声音事件列表后，两个地方使用同一个结果：
1. `trim_segments_by_sensevoice()` — 砍掉非人声区间的 Whisper 段落
2. 给每个段落打标签 `seg.sensevoice_tag` — 供后续交叉验证参考

**结论**：在新流水线中，SenseVoice 也只跑一次——只是顺序提前，在 Whisper/千问转录之前就跑完，画出"声音地图"。后续三层防线都引用这张地图。

---

#### 争议二："第一层：SenseVoice标了非人声，Whisper写了字直接判幻觉"——为什么只针对Whisper？千问呢？

**用户的质疑**：
1. 千问在同一段非人声音频上也会产生输出。如果 SenseVoice 标了"Breath"，两种可能性都存在——千问可能没说话，也可能说了话
2. 如果只判 Whisper 不管千问，那就漏掉了千问在非人声区域也产生幻觉的场景

**讨论结果**：修改第一层防线设计。从"SenseVoice 一个人判"改为"SenseVoice + 千问双重确认"：

| SenseVoice 标 | 千问说 | 结论 | 动作 |
|-------------|------|------|------|
| 非人声 | 没说话 | 两人一致 | Whisper写了字 → 自动判幻觉 |
| 非人声 | 说了话 | 两人矛盾 | **不自动判。** 标记可疑，留给人工或LLM确认 |

SenseVoice 不是法官。它是证人。千问是第二个证人。两个人一致 → 置信度高。两个人矛盾 → 标记待确认。

---

#### 争议三：SenseVoice 能百分百确认就是非人声吗？

**用户的质疑**：如果 SenseVoice 不能百分百确认，非人声区域的"自动判幻觉"就会误删真实对话。

**核实数据**（job 1b520de51c）：24 分钟视频，SenseVoice 只识别了 5 个声音事件：

```
标签分布: {'Speech': 3, 'Breath': 2}
SenseVoice 修剪: 丢弃 109 段, 保留 266 段
```

5 个标签砍掉了 109 段（29% 的内容）。如果其中一个标签是错的——比如某段对话被标成了"Breath"——真实的对话就被删了。

**修正方案**：SenseVoice 不单独做删除决定。第一层防线改为双重确认：
- SenseVoice 说"非人声" + 千问也说"没说话" → 置信度高，可自动判。但即便如此，也只标注不删除——在交叉验证报告中标为"潜在幻觉"，不直接从字幕中删除
- SenseVoice 说"非人声" + 千问说了话 → 标记可疑。交给 LLM 翻译确认
- 现在的做法（SenseVoice一个人删掉109段、不经过千问确认）需要改

**用户的担忧**：这个双重确认机制仍然不是完美的。千问也可能在非人声区域说话（千问幻觉）。不过当前没有更好的解法——SenseVoice + 千问双重确认已经比 SenseVoice 一个人决定要好。

---

#### 争议四：全文对比 vs 按段对比

**讨论过程**：
1. 用户最初提出：把千问和 Whisper 的全文拿出来，像两篇文章一样对比——"方案一"
2. Steve Jobs 审查后认为：纯全文对比只有一个数字结论，看不到问题发生在哪个位置
3. 讨论中产生了三个对比方案：
   - A) 整篇算一个比例（两篇文章所有词干拿出来算共享率）
   - B) 切成小窗口，每个窗口内比词干（不看段号，但保留词的时间位置）
   - C) 像 Word 文档差异对比（完全不看时间，逐词标出差异）
4. 经过多轮讨论和乔布斯审查，确定 **B + A 组合**——B 做主力（窗口内比对），A 做统计（汇总一致率）。C 被否决（只会告诉你"字不一样"，不能告诉你"意思一不一样"）

---

#### 争议五："裁尾巴"对中文无效怎么办？

**讨论结果**：每种语言配不同的钥匙。中文不需要裁（汉字本身不变形）。中文是最简单的交叉验证语言。

| 语言 | 方式 | 理由 |
|------|------|------|
| 中文 | 不裁，直接逐字比 | 汉字不变形，"钱"永远是"钱" |
| 英语 | Porter Stemmer | running→run, walked→walk |
| 俄语 | Snowball Stemmer | деньги/денег→ден |
| 日语/韩语 | 滤助词 | は/が/を/에/를 等不承载核心意思 |

**未解决的问题**：英语不规则变形（ran/run, went/go）裁不掉。日语助词过滤后可能误删有意义的短词。每种语言的"词干重叠门槛"需要单独校准。这些需要真实数据才能定。

### 5.1 进度显示粒度过粗（P159）

**现象**：前端进度条在"转录中"阶段卡住不动。内部有三个子阶段（Whisper ~30min → SenseVoice → Qwen3），但 Worker 始终向前端发同一条步骤消息。

**原因**：[`v2/backend/worker.py`](v2/backend/worker.py) 中 `emit("progress")` 在转录阶段只发了单一的步骤描述。

**方案**：后端 emit 文字从"转译中"改为"Whisper转录中…""交叉验证中…(Qwen3)""声音分类中…(SenseVoice)"。只改后端 emit 文字，不碰前端。不加新字段。

**状态**：推迟到 Phase 2，与 PySide6 前端重写一起做。
