# 用户体验审查报告 — Steve Jobs 视角

审查日期：2026-06-09
审查范围：Video Subber V3.07 Web UI + 后端进度报告
审查人：Steve Jobs（角色扮演）

---

## UX-1：进度条是假的

**严重度：** P0（用户体验核心缺陷）

**现象：**
用户点"开始"后，界面显示"正在识别语音…"和一个蓝色脉冲进度条。这个状态持续 25 分钟，进度从 10% 跳至 25% 后长时间不动。背后的实际流程：Whisper 转录 → Qwen ASR 交叉验证 → FA 词级对齐 → SenseVoice 声音分类 → 五层过滤。五个步骤全包在 "transcribe" 一个阶段里。

**根因：**
`worker.py` 把五个子步骤全部封装在 `transcribe_v2()` 一个函数调用中。前端只收到一条阶段名 "transcribe" 和一个笼统的百分比。子步骤的日志全部写在后端日志文件中，不通过 WebSocket 推送给前端。

**用户影响：**
用户在 25 分钟的焦虑等待中以为程序卡死，对产品的信任每多等一分钟就减一分。

**建议方案：**
将 "transcribe" 阶段拆分为四个子阶段，每条用一句话描述，通过 WebSocket 推送真实进度：
1. "正在将声音转成文字…"（Whisper，10-20%）
2. "正在核对文字准确度…"（Qwen ASR，20-25%）
3. "正在给每个词标记时间…"（FA 对齐 + SV，25-33%）
4. "正在过滤不可靠的字幕…"（五层过滤，33-35%）

改动位置：`worker.py` stderr_progress 调用 + `transcriber_v2.py` 内部增加 progress_callback 调用。

## UX-2：警告信息制造焦虑但不提供解决方案

**严重度：** P0（用户会因此放弃使用产品）

**现象：**
> ⚠ 音频质量较差（54% 字幕存疑），建议手动校对后使用

54% 的数字让用户直觉认为"这个工具不行，一半都是错的"。但实际上大部分存疑字幕的翻译质量合格——只是背景音乐导致 Qwen ASR 无法有效交叉验证，触发了 L2 的 YELLOW 标记。

**根因：**
`showQmWarning()` 函数（index.html:1276-1284）用 qm/total 比例一刀切判定。超过 15% 就显示红色警告，超过 5% 显示黄色。没有区分"真正错误"和"因音频条件无法确认"两种情况。

**用户影响：**
用户收到错误质量信号，可能放弃继续使用该产品，或对输出内容产生不必要的不信任。

**建议方案：**
重新设计警告文案为上下文感知版本：

> 字幕处理完成。您的视频全程有背景音乐，部分字幕的校对标记可能偏多。这不影响翻译质量——标记 [?] 的段落翻译大多数是准确的，只是模型在音乐干扰下无法 100% 确认。建议快速浏览标 [?] 的段落。

同时，警告颜色分级改为：
- 红色：仅当有实际丢弃或翻译失败的段落
- 黄色：存疑比例较高但无实际丢段
- 绿色/无警告：正常

## UX-3：设置面板在任务运行期间被完全锁死

**严重度：** P1（严重影响操作灵活性）

**现象：**
用户点击"开始"后，所有设置控件（输出方式、字幕样式、翻译模式、模型选择等）全部变灰不可操作。持续 30 分钟直到任务完成。如果用户在运行 2 分钟后发现选错了输出模式，只能取消整个任务重来。

**根因：**
`lockUI()` 函数（index.html:1151）给所有设置控件添加 `disabled-ctl` 类，并通过 `settingsLocked` 全局变量阻止修改。设计意图是"设置变了任务参数就不一致了"。

**用户影响：**
一次小小的设置失误需要付出 30 分钟的重新等待代价。用户感到被工具控制，而不是控制工具。

**建议方案：**
- 允许修改"当前任务尚未用到的设置"（如字幕样式在识别阶段还没用到）
- 添加"排队修改"机制：提示"当前任务将沿用原设置，新设置将在下次处理时生效"
- 至少允许用户取消单个任务而不影响其他任务

## UX-4：模型和翻译的故障对用户完全不可见

**严重度：** P1（用户不知道质量损失的原因）

**现象：**
FA 对齐器加载失败 → 静默跳过。Qwen ASR 不可用 → 静默降级。LLM 翻译超时 → 自动切到免费引擎（Google/Bing）。用户永远不会知道这些事情发生了。用户只知道"字幕好像不太准"——不知道为什么。

**根因：**
后端所有子系统的可用性检测和降级逻辑通过 `_log.warning()` 写入日志文件。前端没有接收和处理这些警告的机制。WebSocket 只推送 progress 和 done 两种消息类型。

**用户影响：**
用户无法判断输出质量问题的来源。如果 FA 跳过了，用户不知道字幕时间戳就是 Whisper 的粗略估计而非 FA 的精确对齐。

**建议方案：**
任务完成后在前端显示处理摘要卡片：

```
处理详情
─────────────────
Whisper 语音识别   ✅ 正常 (large-v3, 515 段)
Qwen ASR 交叉验证  ✅ 正常 (MLX 加速)
FA 词级对齐        ✅ 正常 (3078 词)
SenseVoice 声音分类 ✅ 正常
翻译引擎           DeepSeek (489/491 成功)
字幕质量           54% 标记存疑 (背景音乐导致，翻译质量可靠)
```

每个子系统的状态在任务完成时由后端汇总为一条 JSON 消息，通过 WebSocket 推送。

## UX-5：已完成任务阻塞新任务

**严重度：** P1（阻塞基本操作流程）

**现象：**
用户处理完一个视频后，想用不同设置重新处理同一个视频。系统显示"检测到任务已完成"，开始按钮灰掉。用户必须手动清缓存、重启服务才能重新开始。

**根因：**
`handleFoundJob()` 函数检测到相同视频的已完成任务后，显示 toast 提示但不清除旧状态。用户没有重新处理的入口。

**用户影响：**
用户需要求助开发者才能完成一个基本操作（重新处理同一个视频）。

**建议方案：**
检测到已完成任务时，显示显式的操作入口：
- "此视频已处理过。修改设置后点击下方按钮重新处理。"
- 添加"重新处理"按钮，点击后自动清除旧任务缓存并提交新任务。
- toast 提示改为持久的内联提示，而非 2 秒自动消失。

## UX-6：下载按钮和输出文件缺少用户友好的说明

**严重度：** P2（可发现性问题）

**现象：**
任务完成后，下载区显示"下载视频"和"下载 SRT"两个按钮。非技术用户不知道 SRT 是什么文件格式，也不知道这个 SRT 里是原文字幕还是翻译后的字幕。如果用户选了"封装字幕"，视频文件本身已经包含字幕了，为什么还要下载 SRT？

**根因：**
`renderCardDone()` 函数使用固定的"下载视频"/"下载 SRT"标签。没有区分输出模式和内容类型。

**用户影响：**
用户下载了文件但不知道它是什么、怎么用。非技术用户的挫败感。

**建议方案：**
根据输出模式调整下载按钮文案：
- 烧录模式：下载视频（已烧录字幕）| 下载字幕文件（SRT 格式，可用记事本打开）
- 封装模式：下载视频（播放时可开关字幕）| 下载字幕文件
- 仅字幕模式：下载字幕文件（SRT 格式）| 下载原文字幕（如有）

## 总结

六个问题按优先级排列：

| # | 问题 | 严重度 | 用户感知 |
|---|------|:------:|---------|
| UX-1 | 进度条是假的 | P0 | "程序卡死了吗？" |
| UX-2 | 警告信息恐吓用户 | P0 | "这工具不能用" |
| UX-3 | 设置面板锁死 | P1 | "我点错了，要等半小时" |
| UX-4 | 故障静默 | P1 | "字幕为什么不准？" |
| UX-5 | 已完成任务阻塞 | P1 | "怎么重新跑？" |
| UX-6 | 下载按钮不清晰 | P2 | "这是什么文件？" |

核心主题：**信息不对称。** 引擎极好，但方向盘和仪表盘极差。用户坐在一辆没有仪表盘的车里，看不见速度、不知道还剩多远、不知道哪个零件在运转。到达目的地后，仪表盘亮了一排红灯，但它不说话，用户只能猜。
